AWS에서 Synopsys VCS / Verdi 협업 환경 구축하기
— User A ↔ User B 격리 + Shared 협업

기존 ParallelCluster + FSx for OpenZFS를 확장하여, User A(RTL 준비·컴파일)와 User B(내부 타팀, 시뮬레이션·디버깅)가 서로의 Private Area는 볼 수 없고 Shared Area만 공유하는 환경을 콘솔부터 단계별로 구성하는 방법.

대상 인프라 ParallelCluster v3 · FSx OpenZFS · Amazon(NICE) DCV 리전 ap-northeast-2 (서울) 사용자 같은 AWS 계정 내 2인 (내부 타팀)
한 문장 요약

격리는 두 겹 — 파일은 리눅스 그룹 권한, AWS 리소스는 IAM 그룹으로 한다. RTL 원본은 S3에 두고 컴파일 노드가 로컬로 복사(aws s3 sync)해 읽어 컴파일하며(S3 직접 마운트는 심링크·성능 문제로 비권장), 결과 simv 한 묶음을 OpenZFS /shared에 저장한다. 그러면 User B 그룹(타팀 여러 명)은 소스 없이도 그 simv를 Slurm으로 병렬 실행해 fsdb 파형을 만들고 GPU + DCV 데스크톱의 Verdi로 분석한다.

1핵심 원칙 — 격리는 IAM이 아니라 리눅스 권한이 한다

이 한 가지를 헷갈리면 전체 설계가 틀어집니다. 그림의 "Private Area / Shared Area" 벽은 AWS IAM이 아니라 리눅스 파일 권한(uid/gid, mode)으로 세웁니다.

계층무엇을 통제하나User A/B 격리에 쓰나?
IAM (사용자·역할)AWS API·리소스 접근 (EC2 시작, S3 버킷, pcluster 명령 등)부분적 — S3 원본 접근 통제엔 사용
Linux / POSIX 권한파일시스템 접근 (홈 디렉토리, 프로젝트 폴더, simv, fsdb)✅ 예 — 이걸로 격리한다
검증됨 primary

ParallelCluster는 IAM을 두 계층에서만 요구합니다 — ① pcluster CLI를 쓰는 사람의 권한, ② 클러스터 인스턴스가 동작하기 위한 역할. 즉 IAM은 "누가 클러스터를 관리·조작하나"만 담당하고, Private/Shared 파일 격리는 리눅스 uid/gid + 파일 권한으로 설계해야 합니다. (AWS ParallelCluster UG — iam-roles-in-parallelcluster-v3)

그룹으로 관리하기 — IAM 그룹과 리눅스 그룹을 둘 다 만든다

User A/B를 그룹으로 묶어 관리하려는 방향은 맞습니다(특히 User B가 타팀 여러 명). 다만 IAM 그룹만으로는 파일 격리가 안 됩니다. VCS가 /shared/proj/simv를 열 때 커널은 IAM을 보지 않고 그 프로세스의 리눅스 uid/gid와 파일 mode만 봅니다. 그래서 같은 사람들을 양쪽 레이어에 각각 그룹화합니다.

하려는 것IAM 그룹으로?실제로 되는 도구

두 그룹이 격리를 두 겹으로 만든다

리눅스 그룹(team_a/team_b/eda_proj)은 파일시스템 격리·협업을, IAM 그룹(EDA-TeamA/EDA-TeamB)은 S3 RTL 원본과 AWS 리소스 격리를 담당합니다. 결과적으로 RTL은 IAM(S3에서 team_b Deny)과 POSIX(파일 권한) 두 겹으로 보호됩니다. 사람 계정 자체는 노드 간 uid/gid 일관성 때문에 AD/LDAP로 관리하는 것이 ParallelCluster 다중사용자의 정공법입니다(§11 참고).

이 흐름이 요구사항을 그대로 구현 — 격리가 두 겹

RTL 원본이 S3에만 있고 컴파일 노드가 잠깐 로컬로 받아 쓰므로 team_b는 RTL을 볼 수 없고(격리), simv·fsdb만 /shared에 있어 team_b는 "실행·분석만" 합니다. RTL 격리가 ① IAM 그룹 정책(S3 버킷 Deny) + ② 컴파일 노드 로컬 복사본은 노드 종료 시 소멸 두 겹으로 보장됩니다. 파일 협업 격리는 리눅스 그룹 + 0700/2775가 담당합니다.

3스토리지 티어링 — S3 vs OpenZFS 역할 분담

"Shared Area를 그냥 S3에 두면 안 되나?"에 대한 정답은 "활성 작업은 OpenZFS, 원본·아카이브는 S3"로 나누는 것입니다.

왜 활성 Shared Area를 S3에 직접 두면 안 되나 primary

  • Mountpoint for Amazon S3는 공식적으로 "기존 파일 수정 불가, 디렉토리 삭제 불가, 심볼릭 링크·파일 잠금(file locking) 미지원". VCS 컴파일은 csrc/·simv.daidir를 in-place로 수정하고 심링크·락을 쓰므로 빌드·시뮬이 깨집니다. (S3 UG — mountpoint)
  • 격리 모델 불일치: 우리 설계의 A/B 격리는 POSIX(0700, setgid) 기반인데, S3 접근제어는 IAM(객체) 기반이라 chmod 권한 모델이 그대로 매핑되지 않습니다.
  • Verdi의 .fsdb 랜덤 액세스 패턴은 객체 스토리지에 부적합.

S3가 정답인 용도

  • RTL 릴리스 스냅샷 · 버전 관리 · team_a만 접근하는 원본 저장
  • 시뮬레이션 결과(fsdb, 로그) 장기 아카이브 — lifecycle로 저비용 계층 이동

RTL 읽어 컴파일 — "S3 직접 마운트"가 아니라 "로컬 복사(sync)"

RTL은 파일 하나가 아니라 파일 트리입니다 — filelist.f, 다수의 `include(+incdir), SystemVerilog package, 매크로, 그리고 종종 심볼릭 링크로 연결된 IP/라이브러리. VCS는 이 작은 파일 수백~수천 개를 랜덤하게 열고 stat합니다. 이 패턴이 S3 마운트의 약점과 정확히 겹칩니다.

S3 직접 마운트복사(sync) 후 컴파일 권장
심볼릭 링크❌ 미지원 → 트리에 심링크 있으면 컴파일 실패✅ 정상
파일 락❌ 미지원✅
수천 개 include 랜덤 읽기🐢 파일마다 S3 요청 → 느림⚡ 로컬 속도
재현성버킷/네트워크 상태 의존스냅샷 고정
결정타는 심볼릭 링크 primary

Mountpoint for S3는 심링크를 지원하지 않는데, 실무 RTL 저장소는 IP/라이브러리 링크에 심링크를 흔히 씁니다. 링크 하나만 있어도 컴파일이 깨집니다. 그래서 RTL은 POSIX 파일시스템으로 복사(aws s3 sync)한 뒤 컴파일하는 것이 EDA 표준 관행입니다. S3 직접 마운트는 "심링크 없고 include 단순한 소규모"에서만 예외적으로 씁니다. 구체적 절차는 §4·§6 참고.

OpenZFS는 Shared 전용으로 써도 된다

이 설계에서 RTL 원본은 S3, 컴파일 복사본은 노드 로컬, simv·fsdb는 /shared에 갑니다. 남는 Private(home)은 개인 스크립트·셸 설정·SSH키 정도로 가볍기 때문에, home은 EFS 또는 head node NFS 기본값으로 두고 비싸고 빠른 OpenZFS는 협업이 실제 일어나는 /shared에 집중시키는 것이 합리적입니다. 단, home도 반드시 공유(네트워크) 스토리지 위에 있어야 하며(컴퓨트 노드가 홈·SSH키를 같은 경로로 봐야 함), Private 격리는 어디에 두든 0700이 담당합니다.

중요 — OpenZFS는 S3 네이티브 연동이 없다 primary

FSx for Lustre는 Data Repository Association(DRA)으로 S3 버킷을 자동 import/export하지만, FSx for OpenZFS는 이 기능이 없습니다. 따라서 S3 ↔ OpenZFS 이동은 aws s3 sync 또는 AWS DataSync로 스크립트/스케줄해야 합니다. 자동 S3 연동이 핵심이면 스테이징용으로 FSx Lustre를 병행하는 선택지도 있으나, 2인 규모에는 aws s3 sync로 충분합니다.

4VCS / simv / fsdb 기본 개념

VCS는 컴파일러입니다. gcc가 .c → a.out을 만들듯, VCS는 RTL(Verilog/SystemVerilog) → simv(실행 가능한 시뮬레이터)를 만듭니다.

RTL 소스 VCS 컴파일 실행 파일 design.v, tb.v ─────────────────────▶ simv (사람이 쓴 코드) (vcs -sverilog ...) (컴파일 결과물)

VCS는 컴파일 방식 시뮬레이터라, RTL을 기계어로 컴파일해 진짜 리눅스 바이너리 simv를 뽑습니다. 그래서 ./simv 실행에는 RTL 소스가 필요 없습니다 — 디자인이 이미 simv 안에 박혀 있으니까요. 이 성질이 "User B는 A가 준비한 환경을 실행만" 요구를 자연스럽게 성립시킵니다.

simv는 혼자 다니지 않는다 — 한 묶음(bundle)

/shared/proj/build/ ├── simv ← 실행 파일 (User B가 ./simv 로 실행) ├── simv.daidir/ ← 디자인 DB (실행에 필수, 함께 있어야 함) │ └── kdb/ ← Verdi 디버깅용 Knowledge DB (vcs -kdb 옵션) └── csrc/ ← 중간 산출물 (증분 재컴파일용)
컴파일 입출력 규칙 — 입력은 로컬 복사본, 출력은 Shared

① 입력: RTL은 S3에서 컴파일 노드 로컬로 복사(aws s3 sync)해 읽습니다(S3 직접 마운트는 심링크·성능 문제, §3 참고). ② 출력: simv.daidir에는 컴파일 당시 절대경로가 박히므로, 만들어 옮기지 말고 출력 타겟(-o)을 처음부터 /shared로 지정하세요.

# team_a 컴파일 노드: RTL을 S3에서 로컬로 받아 컴파일, 산출물만 Shared로
LOCAL=/tmp/build.$SLURM_JOB_ID
mkdir -p $LOCAL && cd $LOCAL
aws s3 sync s3://myco-rtl/proj-x/rtl  ./rtl    # ← 트리 통째 복사 (심링크도 실체화)
vcs -full64 -sverilog -kdb -debug_access+all \
    -f ./rtl/filelist.f \                    # 입력 = 로컬 복사본 (빠름·심링크 OK)
    -o /shared/proj/build/simv            # 출력 = OpenZFS Shared로 직접
# 노드 종료 시 /tmp의 RTL 복사본은 소멸 → team_b에 잔류물 없음(격리)
복사 목적지 두 선택지

① 컴파일 노드 로컬 디스크(/tmp, 위 예시) — 가장 빠르고, 노드 종료 시 소멸해 격리가 자동. 일회성 컴파일에 기본 권장.
② OpenZFS 프라이빗 staging(/shared/staging/rtl, 0700 team_a) — 재컴파일·재현이 필요할 때. 단 OpenZFS가 "Shared 전용"에서 살짝 벗어남.

실행하면 무엇이 나오나

./simv +testcase=test1 → test1.fsdb (파형) → verdi -ssf test1.fsdb → GUI 파형 분석

5시뮬레이션 실행 — Slurm 병렬 regression

흔한 오해 — "simv를 각 머신으로 받아서"

복사하지 않습니다. simv는 OpenZFS /shared/proj/build/에 딱 하나 있고, 모든 컴퓨트 노드가 그 파일시스템을 NFS로 같이 마운트합니다. 노드가 10대여도 각자 같은 경로 /shared/proj/build/simv에서 같은 파일을 바로 읽습니다. 복사 단계가 없습니다.

FSx OpenZFS /shared/proj/build/simv (원본 1개) │ (NFS 마운트 — 복사 아님) ┌──────────┬────────┼────────┬──────────┐ node1 node2 node3 node4 node5 ← 전부 같은 simv를 읽음 test1.fsdb test2.fsdb ... ... test10.fsdb └──────────┴────────┼────────┴──────────┘ ▼ FSx OpenZFS /shared/proj/run/ (fsdb들이 여기 모임)

컴파일 1대 vs 시뮬레이션 N대

작업병렬화필요 리소스
VCS 컴파일단일 노드 (내부 gcc 단계만 -j N 멀티코어)CPU 좋은 1대
시뮬레이션 실행테스트케이스 수백 개를 노드에 분산 (regression)여러 노드

즉 클러스터가 필요한 건 "많은 시뮬레이션을 동시에" 돌릴 때이지 컴파일 자체가 아닙니다.

Slurm Job Array로 테스트케이스 분산

ParallelCluster의 스케줄러는 Slurm입니다. 서버를 수동으로 띄우는 게 아니라, 잡을 큐에 넣으면 ParallelCluster가 필요한 만큼 노드를 자동으로 켜고(0→N), 끝나면 자동으로 끕니다.

# run_regression.sbatch
#!/bin/bash
#SBATCH --partition=compute
#SBATCH --array=1-200        # 테스트 200개 → 200개 작업으로 분산
#SBATCH --job-name=vcs_reg

# 이 array task가 담당할 테스트케이스 하나 선택
TEST=$(sed -n "${SLURM_ARRAY_TASK_ID}p" /shared/proj/testlist.txt)

# ★ 테스트마다 전용 작업 폴더 (fsdb 덮어쓰기 방지)
RUNDIR=/shared/proj/run/$TEST
mkdir -p $RUNDIR && cd $RUNDIR

# 공유된 simv를 실행 (복사 없이 절대경로로 실행)
/shared/proj/build/simv +testcase=$TEST -l $RUNDIR/sim.log
# → 이 폴더에 $TEST.fsdb 파형 생성
sbatch run_regression.sbatch     # 200개가 큐로 → 노드 자동 확장되며 병렬 실행
squeue                            # 진행 상황 확인
실무 함정 2가지

① 작업 폴더 분리 필수. 모든 테스트를 같은 디렉토리에서 돌리면 fsdb·런타임 임시파일이 서로 덮어씁니다 → 테스트마다 run/$TEST/ 전용 폴더에서 cd 후 실행. (simv는 읽기 전용 공유라 동시 읽기는 문제없음)

② 라이선스 좌석 = 동시 실행 상한. 실행 중인 simv 하나가 VCS 시뮬레이션 라이선스 1개를 씁니다. 좌석이 20개면 200개 잡 중 20개만 동시 실행되고 나머지는 대기(노드가 남아도). 노드 수뿐 아니라 라이선스 좌석 수도 병렬도를 좌우합니다. (SOCA의 license_check 패턴 — 잡 제출 전 여유 확인)

규모 판단

2인 + 단일 테스트벤치 수준이면 이 job-array 분산까지 안 가도 됩니다. 컴파일 1대에서 simv 만들고 몇 개 돌려보는 정도면 충분하며, regression을 수백 개씩 돌리기 시작할 때 비로소 클러스터 병렬이 값어치를 합니다.

6단계별 구축 절차 (콘솔 홈부터)

비용 갈림길 먼저

사용자가 딱 2명이면 Simple AD(무료~저렴)로 충분합니다. AWS Managed Microsoft AD(Standard)는 서울 리전 기준 시간당 요금이 붙어 월 15만원대가 나옵니다. 둘 다 ParallelCluster가 공식 지원하므로 2인 협업이면 Simple AD를 권장합니다. (multi-user-v3)

  1. 콘솔 홈 검색창 → Directory Service → Directories → Set up directory

  5. 생성 후 Directory ID · DNS IP 2개 기록 → ParallelCluster config에 사용
2

사용자·그룹 만들기 — 리눅스 그룹 + IAM 그룹 이원화

(2-1) 디렉토리(AD/LDAP)에 사람 + 리눅스 그룹

도메인 조인된 관리 EC2(또는 Managed AD 관리 도구)에서 생성:

  • 리눅스 그룹 team_a (gid 예: 20001) — userA1, userA2 …
  • 리눅스 그룹 team_b (gid 예: 20002) — userB1, userB2 … (타팀 다수)
  • 공유 협업 그룹 eda_proj (gid 예: 20000) — team_a·team_b 구성원 모두 보조그룹으로 포함
  • 각 사용자 uid는 노드 간 동일하게(AD가 보장)

포인트: 두 팀은 eda_proj를 공유하되 개인 홈은 각자 소유 — 이 두 축이 "공유 + 격리 동시 달성"의 뼈대입니다.

(2-2) IAM 그룹 (AWS 리소스 격리)

→ team_b는 aws s3 sync로 RTL을 받을 수조차 없어, POSIX 이전에 IAM에서 먼저 차단됩니다(격리 첫 겹).

3

S3 버킷 + FSx OpenZFS 준비

검증됨 — ParallelCluster는 FSx OpenZFS를 만들지 않는다

기존 볼륨을 VolumeId로 external attach만 지원(3.2.0+). 콘솔 홈 → FSx에서 OpenZFS 파일시스템/볼륨을 먼저 생성해 두세요. (SharedStorage-v3)

  • S3 버킷 생성 → RTL 원본 프리픽스(예: s3://myco-rtl/proj-x/). 접근은 IAM 그룹 EDA-TeamA에 read/write, EDA-TeamB에 Deny로 통제(§6 STEP 2-2). 결과 아카이브용 별도 버킷도 함께 생성.
  • FSx OpenZFS 볼륨 생성 = /shared 전용(tools + proj). NFS exports에서 클러스터 서브넷 CIDR 허용, POSIX 권한 존중을 위해 root_squash 기본 유지(관리 노드에만 필요 시 no_root_squash). (FSx OpenZFS NFS exports)
  • home 스토리지 — Private가 가벼우므로 EFS 생성(또는 head node NFS 기본값 사용). /home 마운트용.

7POSIX 권한 설계 (Private 격리 + Shared 협업)

그림의 요구사항을 실제로 구현하는 핵심 파트입니다. 표준 리눅스 멀티유저 관행 — setgid/ACL 근거는 리서치에서 supporting claim으로 확인

# === Private Area (home = EFS) — 상호 접근 완전 차단 ===
#     각 사용자 홈은 본인 소유 0700 (예: userA1은 team_a, userB1은 team_b)
install -d -m 0700 -o userA1 -g team_a  /home/userA1
install -d -m 0700 -o userB1 -g team_b  /home/userB1
#  0700 = 소유자만 rwx → team_b는 team_a의 홈 진입 불가 (역도 성립)

# === Shared: 툴 설치 — 모두 읽기/실행, 쓰기는 관리자만 ===
install -d -m 0755 -o root  -g eda_proj /shared/tools

# === Shared: 공동 프로젝트 — 두 팀이 함께 읽고 쓰기 ===
install -d -m 2775 -o root -g eda_proj /shared/proj
#  '2' = setgid → 이 안에서 새로 만든 파일/폴더는 그룹이 자동으로 eda_proj 상속
#  → team_a가 만든 컴파일 산출물을 team_b가 바로 rw 가능
0700 Private — 소유자 전용 0755 공유 읽기 전용 2775 setgid 공동 쓰기

추가 권장

  • 협업자 로그인 프로파일에 umask 002 설정 → 새 파일이 664(그룹 쓰기 가능)로 생성. (기본 022면 그룹 쓰기가 막혀 협업이 깨짐)
  • 더 세밀한 제어가 필요하면 NFSv4 ACL / setfacl로 "특정 사용자에게만 rwx" 부여 가능(그룹 안 만들고도). 기본 ACL(-d)로 상속 지정. (setfacl — supporting)

8Amazon DCV로 Verdi GUI 디버깅

Verdi는 GPU 가속이 유리한 파형/스키매틱 GUI입니다. 사용자별 격리된 원격 데스크톱 세션으로 제공합니다.

간단한 경로 (2인 권장) blog

각 사용자가 SSH 로그인 후, viz 큐에 자기 소유의 DCV 세션을 Slurm 배치 잡으로 제출:

#SBATCH --partition=viz
#SBATCH --exclusive        # 사용자마다 전용 인스턴스 → 세션 격리
#SBATCH --gpus 1           # 사용자별 GPU 할당
dcv create-session $SLURM_JOBID   # 세션 소유자 = 잡 제출한 리눅스 사용자

세션은 잡을 제출한 리눅스 사용자 소유로 생성되므로 User A 세션에 User B가 붙을 수 없습니다(OS 사용자 격리). AD 모드에서는 배치 스크립트의 로컬 password 라인을 제거하고 AD 자격증명으로 인증합니다. Verdi는 이 GPU 세션의 데스크톱에서 실행 → fsdb 파형 디버깅. (HPC blog — elastic viz queues)

규모가 커질 때 (선택) primary

DCV Session Manager(Broker) + Connection Gateway + NLB 조합. Gateway가 다수 DCV 서버의 단일 접속점이 되고, Broker가 Session Resolver로 각 연결을 올바른 호스트로 라우팅합니다. 클라이언트는 NLB주소:8443/?authToken=...#session-id로 접속. aws-samples dcv-samples/cdk/dcv-gw-sm-without-pipelines가 이 스택(Broker 1, Gateway ASG, NLB, IAM/SG)을 그대로 배포합니다. (dcv/sm-admin/configure, dcv-samples CDK)

반증됨 refuted 0-3

"DCV Session Manager의 external authorization server가 세션 접근 인가 메커니즘이다"라는 주장은 검증에서 기각됐습니다. 세션 소유권/접근은 세션 owner + permissions로 통제하는 것이 정확합니다. 대규모 인가 설계 시 이 부분은 DCV Session Manager Admin Guide로 별도 확인하세요.

DCV 라이선스 primary

EC2에서 DCV 서버는 별도 라이선스 서버가 불필요합니다(S3 경유로 라이선스 확인). ParallelCluster가 head node IAM에 필요한 권한을 자동 부여합니다. (dcv-v3)

9Synopsys 라이선스 서버

검증됨 primary

Synopsys Common Licensing(SCL)은 FlexNet 기반으로 두 데몬을 씁니다 — lmgrd(FlexNet 라이선스 매니저)와 snpslmd(VCS/Verdi 등에 feature 라이선스를 서빙하는 Synopsys 벤더 데몬). 클라이언트는 SNPSLMD_LICENSE_FILE(권장) 또는 LM_LICENSE_FILE에 port@host(예: 27020@host)로 서버를 지정하므로, 다수 컴퓨트 노드가 하나의 공유 라이선스 서버를 가리킬 수 있습니다. 단일 리눅스 서버가 네트워크의 모든 클라이언트에 TCP로 서빙합니다. (Synopsys licensing)

  • 라이선스 서버는 고정 ENI/EIP로 hostid 고정 (§6 STEP 5 참고).
  • 동시 실행 simv 수 ≤ 확보한 시뮬레이션 라이선스 좌석 수 (§5 함정 ② 참고).

11주의사항 & 함정

  1. FSx OpenZFS는 ParallelCluster가 안 만든다 → 먼저 콘솔에서 생성 후 VolumeId attach. primary
  2. OpenZFS는 S3 네이티브 연동이 없다 → aws s3 sync / DataSync로 이동. 자동 연동이 필요하면 스테이징에 FSx Lustre(DRA) 고려. primary
  3. S3를 활성 Shared로 직접 쓰면 안 됨 → Mountpoint는 파일 수정·락 미지원, VCS 빌드가 깨짐. S3는 원본·아카이브 전용. primary
  4. RTL은 S3 직접 마운트 말고 로컬 복사 후 컴파일 → RTL 트리의 심볼릭 링크는 Mountpoint에서 미지원이라 컴파일이 깨지고, 수천 개 include 랜덤 읽기도 느림. aws s3 sync로 노드 로컬(/tmp)에 받아 컴파일. primary
  5. 심링크 실체화 → RTL을 S3에 올릴 때 --follow-symlinks(기본)로 실체 파일화하거나, 링크 구조가 의미 있으면 tar로 묶어 올릴 것. 실무
  6. IAM 그룹 ≠ 파일 격리 → IAM 그룹은 S3·AWS 리소스만 통제. 파일 격리(홈 상호차단, /shared 협업)는 반드시 리눅스 그룹 + POSIX 권한으로. 두 그룹을 각 레이어에 병행. primary
  7. 2인이면 AD가 과할 수 있다 → Simple AD로 비용 절감. 단, 무-AD 로컬유저는 노드 간 uid 불일치로 Slurm 스케줄링이 깨질 수 있어 v3.1.1+ 다중사용자에서 비권장. primary
  8. 공식 aws-samples ParallelCluster EDA 워크샵은 "Coming soon" 상태로 미완성 → 턴키 레퍼런스 없음. 완성본은 IBM Spectrum LSF 워크샵(Slurm 아님)뿐. 이 문서의 절차를 조합해 직접 구성해야 함. primary
  9. simv 경로 의존성 → Private에서 만들어 옮기면 simv.daidir 절대경로로 깨질 수 있음. 처음부터 /shared로 컴파일. 실무
  10. umask 함정 → 협업자 umask가 022면 공유영역 그룹 쓰기가 막힘 → 002. 실무
  11. fsdb 덮어쓰기 · 라이선스 좌석 상한 → 테스트별 전용 폴더 + 좌석 수 = 동시 실행 상한. 실무
  12. FlexNet MAC 고정 → 라이선스 서버는 고정 ENI/EIP. primary
  13. DCV 세션 인가 → external authorization server 주장은 반증됨. 세션 owner + permissions로 통제. refuted
